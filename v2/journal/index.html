01 The Problem: The Naive LLM SQL Trap

The goal was simple: let a non-technical stakeholder type "What are the top 5 product categories by revenue in Q3 2025?" and get an answer from the data warehouse. The naive implementation — dump the full schema and the question into an LLM prompt, take the SQL it returns, run it — fails on three vectors that I only fully appreciated after watching it break:

  • Schema context explosion. The warehouse had dozens of tables and hundreds of columns. Dumping all of it consumed thousands of prompt tokens. The LLM's attention drifted, and it started hallucinating column names from tables adjacent to the one being queried.
  • Destructive mutations. The LLM cannot be trusted to generate read-only SQL. An adversarial or just confused prompt could produce DROP TABLE, DELETE FROM, or an unindexed table alteration. My first instinct — a regex blocklist checking for the word "DROP" — was bypassed in minutes.
  • Synchronous blocking. A complex analytical query scanning hundreds of thousands of rows locked the HTTP request-response lifecycle. Reverse proxies like Nginx reset the connection before the query finished.
✏ Before you read on

You have an LLM that can write SQL, and a user asks "What are the top 5 product categories by revenue in Q3 2025?" The warehouse has 40 tables and 300 columns. How do you let the LLM answer this without risking a DROP TABLE, a hallucinated column, or a query that locks the database for 30 seconds? Sketch the validation boundary — where does the LLM stop and deterministic code take over?

The LLM should never touch the execution layer directly. It generates SQL as a candidate string. Deterministic code then does three things: retrieves only the relevant schema slice (not the whole warehouse), parses the SQL into an Abstract Syntax Tree to check for mutations regardless of formatting, and executes it in a sandboxed in-process engine with a timeout and row cap. The boundary is: LLM proposes, code validates, code executes. The LLM has no authority over what runs.

02 What I Tried First

My first approach was a regex keyword blocklist. Before executing the LLM's SQL, I checked whether the string contained DROP, DELETE, INSERT, UPDATE, or ALTER. If it did, I rejected it.

This lasted about ten minutes. The bypass was trivial:

⚠ Regex bypass
-- The regex sees "SELECT", misses the DROP inside the comment
SELECT 1; /* harmless */ DROP TABLE users;

-- Or nested inside a subquery the regex doesn't understand
DELETE FROM (SELECT id FROM orders WHERE status = 'shipped');

Regex operates on strings. SQL is a context-free grammar. You can't evaluate the semantic intent of a query by searching for keywords — you need to parse the structure.

03 The Decision

I weighed four approaches for the safety boundary:

✗
Regex keyword blocklist
Bypassed by comments, nesting, and case variations. Operates on strings, not structure.
✗
Read-only database user
Prevents writes but doesn't prevent Cartesian explosions, connection resets, or hallucinated columns. No resource limits.
✗
Full schema in the prompt
Thousands of tokens, attention drift, hallucinated column names from adjacent tables.
✓
AST validation + DuckDB sandbox + schema retrieval
Parse the SQL into a syntax tree to check mutations structurally. Execute in an in-process engine with a timeout and row cap. Send only the relevant schema slice to the LLM.

The key insight: SQL is a context-free grammar. By parsing it into an Abstract Syntax Tree with sqlglot, we can traverse the tree and evaluate the semantic intent of the query regardless of formatting, comments, or nested subqueries. A Drop node in the AST is a Drop node whether it's wrapped in a comment, split across lines, or buried in a subquery. Regex sees strings; the AST sees structure.

04 Building It

The pipeline has six stages. Each stage has a clear input and output, and the LLM is confined to exactly one of them (stage 2).

The safety gate is a two-stage AST validator. Here is the actual code, with the two stages labelled:

📄 backend/validator.py — Two-Stage AST Safety Gate 
import sqlglot
from sqlglot import exp
from typing import Tuple, Optional, Set, Dict

# Every AST expression type that alters state or metadata
FORBIDDEN_EXPRESSIONS = (
    exp.Drop, exp.Insert, exp.Update, exp.Delete,
    exp.AlterTable, exp.Command, exp.Pragma,
    exp.Create, exp.Merge
)

class SQLASTSafetyValidator:
    def __init__(self, allowed_tables: Set[str], allowed_columns: Dict[str, Set[str]]):
        self.allowed_tables = {t.lower() for t in allowed_tables}
        self.allowed_columns = {
            t.lower(): {c.lower() for c in cols}
            for t, cols in allowed_columns.items()
        }

    def validate(self, sql_query: str) -> Tuple[bool, Optional[str], Optional[exp.Expression]]:
        # Strip markdown code fences if the model wrapped the output
        cleaned = sql_query.strip().removeprefix("```sql").removeprefix("```").removesuffix("```").strip()

        try:
            ast = sqlglot.parse_one(cleaned, read="duckdb")
        except sqlglot.errors.ParseError as pe:
            return False, f"SQL Syntax Parse Error: {pe}", None

        # ── STAGE 1: Structural Mutation Guard ──
        # Traverse the entire tree — a Drop inside a subquery is still a Drop
        for forbidden_node in ast.find_all(FORBIDDEN_EXPRESSIONS):
            return False, f"Prohibited operation '{forbidden_node.key.upper()}' detected.", None

        # Root must be a SELECT or UNION — nothing else is read-only
        if not isinstance(ast, (exp.Select, exp.Union)):
            return False, "Query must be a read-only SELECT or UNION statement.", None

        # ── STAGE 2: Schema Existence Verification ──
        # Every referenced table must exist in the retrieved schema slice
        for table_node in ast.find_all(exp.Table):
            t_name = table_node.name.lower()
            if t_name not in self.allowed_tables:
                return False, f"Table '{t_name}' is not in the authorized schema slice.", None

        return True, None, ast

The find_all traversal is the whole point. It walks the entire tree — a Drop node buried three subqueries deep is still found and rejected. A regex would never see it.

Execution runs in an in-process DuckDB session. Data is partitioned into read-only Parquet tables. The executor wraps every query in an asyncio.wait_for(..., timeout=5.0) circuit breaker and injects a LIMIT 10000 to prevent out-of-memory crashes from accidental Cartesian products.

📄 backend/executor.py — Sandboxed Execution 
import asyncio
import duckdb

async def execute_sandboxed(conn: duckdb.DuckDBPyConnection, sql: str) -> dict:
    # Inject a row cap — the LLM can't be trusted to add its own LIMIT
    if "LIMIT" not in sql.upper():
        sql = sql.rstrip(";") + " LIMIT 10000"

    try:
        # 5-second circuit breaker — a Cartesian product will hit this
        result = await asyncio.wait_for(
            asyncio.to_thread(conn.execute, sql),
            timeout=5.0
        )
        rows = result.fetchall()
        columns = [d[0] for d in result.description]
        return {"success": True, "columns": columns, "rows": rows}
    except asyncio.TimeoutError:
        return {"success": False, "error": "Query exceeded 5-second timeout. Likely a Cartesian product on a non-unique column."}
    except Exception as e:
        # The traceback is fed back to the LLM for the self-correction retry
        return {"success": False, "error": str(e), "traceback": traceback.format_exc()}

05 What Went Wrong

💥 Things that broke before the system worked
  • The Cartesian product. The LLM joined a 50,000-row table with a 50,000-row table on a non-unique column — 2.5 billion intermediate tuples. DuckDB's memory spiked and the process crashed. Diagnosis: the LLM doesn't know which columns are unique. Fix: the asyncio.wait_for timeout and the LIMIT 10000 injection. The timeout catches it; the row cap prevents the memory spike.
  • Markdown codeblocks in model output. The LLM wrapped its SQL in ```sql ... ``` fences. sqlglot couldn't parse the fences and returned a parse error. Diagnosis: checked the raw string the validator received — it had backticks. Fix: the removeprefix("```sql").removesuffix("```") cleaning step before parsing.
  • Schema retrieval misses. A table named fulfilment_centers was never retrieved when the user asked about "warehouses" — the names shared no vocabulary. Diagnosis: the retriever is keyword-based, so a question phrased entirely outside the schema's vocabulary misses relevant tables. Accepted trade-off: in that case, the system leans on the model's general knowledge rather than the retriever. It's a known limitation, not a bug.
  • Self-correction scope. I initially tried to let the self-correction retry fix mutation attempts too — feed the rejection message back and let the LLM try again. This was wrong: a DROP TABLE attempt is reported, never repaired. The retry is reserved exclusively for queries that parse and pass the AST gate but fail on execution (a type cast error, a missing column alias). One retry, then give up.
💡 The Takeaway

The boundary between "what the LLM controls" and "what deterministic code controls" is the whole system. The LLM generates a candidate. Deterministic code validates it, executes it, and decides whether to retry. Never let the LLM touch the execution layer — and never trust a string filter when you can parse the structure.

01 The Problem: Webhook Deadlines & Line Hallucinations

I wanted to build a GitHub App that automatically reviews pull requests — reads the diff, fetches relevant context, asks an LLM for findings, and posts inline comments on the lines it found issues with. Three constraints shaped everything:

  • The 10-second webhook deadline. GitHub requires an HTTP 2xx response almost immediately. If the handler does diff fetching, context retrieval, and multi-turn LLM reasoning synchronously, GitHub triggers delivery timeouts and flags the app as unhealthy.
  • Line-number hallucinations. LLMs are notoriously bad at exact line counting. When reviewing a diff hunk, the model would frequently comment on line numbers that were not modified. GitHub's Review API then rejected the comment with a 422 Unprocessable Entity.
  • Code privacy. Many organizations refuse to send proprietary source to hosted commercial LLMs. The agent had to support local, air-gapped models without changing its core workflow logic.
✏ Before you read on

GitHub gives you 10 seconds to respond to a webhook before it times out. Your review takes 15–30 seconds on a local model. How do you reconcile these two timescales without losing the review? And once the review is done, how do you stop the model from commenting on lines that don't exist in the diff? Sketch the architecture — what happens in the webhook handler, what happens after, and where the validation sits.

Split the timeline. The webhook handler does three things and nothing else: verify the HMAC signature, apply a rate limit, and enqueue the job to a worker queue (Celery + Redis). Then it returns 200. The actual review — diff parsing, context retrieval, model inference, comment publishing — happens on the Celery worker, with no deadline pressure. For the line-number problem: after the model emits findings, a deterministic validation node builds a set of actually-modified line numbers from the parsed diff and drops any finding whose line number isn't in that set. The model never reaches GitHub directly — its output passes through a hard filter first.

02 What I Tried First

I ran the entire review synchronously inside the webhook handler. The FastAPI endpoint fetched the diff, called the LLM, parsed findings, and posted them to GitHub — all before returning a response.

On a hosted model with a 2–5 second response time, this sometimes worked. On a local model (Ollama running Qwen 2.5 Coder on CPU), the review took 15–30 seconds. GitHub timed out at 10, retried the delivery, and the app got a duplicate review on top of the timeout flag.

The second problem appeared immediately after: the model commented on line 47 of a file where the diff only touched lines 30–35. GitHub returned 422 Unprocessable Entity. The review had good content but it couldn't be anchored to the diff.

03 The Decision

✗
Synchronous review in the webhook handler
Exceeds GitHub's 10-second deadline on any non-trivial model. Duplicate deliveries on retry.
✗
Send the whole repository to the model
Privacy risk, token cost, and relevance noise. Most of the repo is irrelevant to any single diff.
✓
Async queue + LangGraph state machine + line boundary filter
Webhook verifies and enqueues in < 50ms. Worker runs a typed state graph. A hard filter drops findings not anchored to modified lines before they reach GitHub.

I modeled the review pipeline as a LangGraph StateGraph — a cyclic, deterministic state machine with strictly typed state. Each node has a defined input and output, so the pipeline is inspectable: you can trace exactly which node produced a finding and which node validated it. The model backend is pluggable behind a BaseLLMBackend interface — switch LLM_BACKEND=ollama or LLM_BACKEND=anthropic and the state machine and GitHub integration don't change.

04 Building It

The pipeline is a linear LangGraph state machine with five nodes. The state is a Pydantic-typed dict that flows through each node:

📄 agent/state_machine.py — LangGraph Review Pipeline 
from typing import TypedDict, List, Dict, Any, Optional
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, END

class ReviewFinding(BaseModel):
    file_path: str = Field(description="Relative path of file in PR")
    line_number: int = Field(description="Exact modified line to anchor review")
    severity: str = Field(description="CRITICAL, WARNING, or STYLE")
    title: str = Field(description="One-sentence summary")
    comment: str = Field(description="Detailed explanation with suggestion")
    suggested_patch: Optional[str] = Field(default=None)

class ReviewState(TypedDict):
    installation_id: int
    repo_full_name: str
    pull_request_number: int
    commit_sha: str
    raw_diff: str
    parsed_hunks: List[Dict[str, Any]]
    raw_model_findings: List[Dict[str, Any]]
    validated_findings: List[ReviewFinding]
    review_status: str

def build_review_graph() -> StateGraph:
    graph = StateGraph(ReviewState)

    # Each node is a pure function: state in, patched state out
    graph.add_node("parse_diff_hunks", parse_diff_node)
    graph.add_node("retrieve_repo_context", fetch_repo_context_node)
    graph.add_node("execute_model_review", model_inference_node)
    graph.add_node("validate_line_boundaries", validate_findings_node)
    graph.add_node("publish_github_review", publish_review_node)

    graph.set_entry_point("parse_diff_hunks")
    graph.add_edge("parse_diff_hunks", "retrieve_repo_context")
    graph.add_edge("retrieve_repo_context", "execute_model_review")
    graph.add_edge("execute_model_review", "validate_line_boundaries")
    graph.add_edge("validate_line_boundaries", "publish_github_review")
    graph.add_edge("publish_github_review", END)

    return graph.compile()

The line boundary validator is the node that was born from the 422 errors. It builds a lookup of which lines were actually modified and drops anything the model invented:

📄 agent/nodes/validator.py — Line Boundary Gate 
def validate_findings_node(state: ReviewState) -> Dict[str, Any]:
    """Drops any finding that points to a line not in the diff."""
    valid_findings = []

    # Build {file_path: set(modified_line_numbers)} from parsed hunks
    hunk_map: Dict[str, set] = {}
    for hunk in state["parsed_hunks"]:
        path = hunk["file_path"]
        hunk_map.setdefault(path, set()).update(hunk["modified_line_numbers"])

    for raw in state.get("raw_model_findings", []):
        try:
            finding = ReviewFinding(**raw)
            # File must exist in the diff
            if finding.file_path not in hunk_map:
                continue
            # Line must be actively modified — not just nearby
            if finding.line_number not in hunk_map[finding.file_path]:
                continue
            valid_findings.append(finding)
        except Exception:
            # Malformed finding — discard silently (accepted trade-off)
            continue

    return {"validated_findings": valid_findings}

The trade-off is real: a valid finding inside a malformed JSON object is lost silently. The alternative — trying to fix malformed output — was worse. The contract is the contract. If the model can't produce it, the finding doesn't ship.

05 What Went Wrong

💥 Things that broke before the system worked
  • GitHub 422 errors. The model commented on line 47 of a file where the diff only touched lines 30–35. Diagnosis: LLMs can't count lines reliably — they see the hunk content but not its absolute position. Fix: the validate_line_boundaries node. Build a set of modified lines from the parsed diff, drop any finding outside it. Zero line-drift leakage after that.
  • Webhook timeouts on local models. A 15–30 second local model run inside the handler exceeded GitHub's 10-second deadline. Diagnosis: the handler was doing work it shouldn't. Fix: move everything to a Celery worker. The handler verifies HMAC, applies a Redis rate limit, enqueues, and returns 200 in under 50ms.
  • Malformed model output. The model sometimes returned findings missing the line_number field or with severity set to an unrecognised string. Diagnosis: the Pydantic ReviewFinding model raised a ValidationError. Fix: the except Exception: continue in the validator silently discards malformed findings. A real finding inside a broken structure is lost — accepted, because the alternative (lenient parsing) would let garbage through.
  • Context that was too rich. I initially sent the full file contents around each hunk to give the model more context. This blew the token budget and introduced noise — the model started commenting on code outside the diff. Fix: a thin context layer only: the repo tree, the README, and the detected language. Changed hunks plus this thin layer is the sweet spot.
💡 The Takeaway

When an external system imposes a deadline, your handler's job is to acknowledge — not to work. Move the work behind a queue. And when an LLM produces structured output that targets a specific location (a line number, a file path), never trust the location — validate it against ground truth before acting on it. The model proposes the comment; the diff decides whether it can be posted.

01 The Problem: Unbounded Infrastructure AI

The idea: an agent that reads Prometheus alerts, gathers diagnostic context, and takes a recovery action — restart a container, scale a replica, notify an engineer. The danger is obvious. If the model hallucinates during an incident:

  • It might restart a database replica during replication catch-up, corrupting the cluster.
  • It might execute an unbounded shell command that escalates a minor memory leak into a cascading regional outage.
  • It operates as a black box: after an incident, human operators have no verifiable record of why the agent chose a specific destructive action.

I needed the agent to be useful — to actually reduce incident response time — without the risk of it making things worse on its own.

✏ Before you read on

An AI diagnoses a memory leak in the payment service and proposes restarting the container. The diagnosis is 88% confident. Do you let it restart? What conditions would you check before allowing autonomous execution? And what happens when a condition fails — does the action just not run, or does something else happen? Sketch the decision boundary.

Four conditions, all conjunctive — every single one must pass. (1) Confidence at or above a threshold (0.75). (2) The proposed action is on a strict allowlist of low-risk operations. (3) The blast-radius impact of the target service is not HIGH. (4) The service is not flagged for mandatory human approval. If all four pass, the action runs automatically with one retry on failure. If any one fails, the action doesn't just silently not run — it goes to a human approval queue with the full diagnosis, evidence, and the gate's rejection reason visible. And every decision, whether auto-executed or queued, is written to an immutable audit trail. The AI never executes anything directly. It proposes; the gate decides.

02 What I Tried First

My first version let the LangGraph agent propose an action and execute it in the same node. The diagnosis and the execution were one step. If the model said "restart the container," the Docker SDK restarted it.

This felt fine in testing against deliberately faulty demo services. But the moment I thought about what could go wrong in a real incident, the design fell apart. The model could be 88% confident and still be wrong. A confident but wrong restart of a database replica during replication catch-up would corrupt the cluster. There was no boundary between "the AI thinks this is a good idea" and "this is safe to do."

A single confidence threshold isn't enough. 88% confidence on a container restart is fine. 88% confidence on a database failover is not. The risk of the action matters as much as the confidence in the diagnosis.

03 The Decision

✗
AI proposes and executes directly
No safety boundary. A confident but wrong action has no gate. Black box — no record of why.
✗
Single confidence threshold
Insufficient. High confidence on a high-risk action is still dangerous. Doesn't account for blast radius or service-specific policies.
✓
AI proposes; deterministic 4-condition gate decides; audit trail records
The model's output is a suggestion, never a command. Four conjunctive conditions. All must pass. Any failure routes to a human approval queue with full evidence. Every decision is logged.

The central invariant: the AI diagnostic model only proposes actions; deterministic Python code decides whether to execute or escalate. The gate is conjunctive — all four conditions must hold. This makes it impossible for a persuasive explanation to talk past the gate. The model can produce the most eloquent diagnosis in the world; if the action isn't on the allowlist, it's not running.

The policy gate is a pure function — same inputs always produce the same decision. No model involvement, no ambiguity:

📄 engine/policy_gate.py — Four-Condition Safety Gate 
from dataclasses import dataclass
from enum import Enum
from typing import Set, Optional

class ImpactRisk(Enum):
    LOW = "LOW"
    MEDIUM = "MEDIUM"
    HIGH = "HIGH"

# Non-negotiable: only these actions may ever run without a human
AUTO_EXECUTION_ALLOWLIST: Set[str] = {
    "restart_container",
    "clear_redis_cache_key",
    "notify_oncall_engineer",
    "scale_read_replica_up"
}

@dataclass(frozen=True)
class PolicyEvaluationResult:
    permitted_for_auto_execution: bool
    requires_human_approval: bool
    rejection_reason: Optional[str]

def evaluate_remediation_policy(
    proposed_action: str,
    confidence_score: float,
    action_risk: ImpactRisk,
    service_requires_manual_gate: bool
) -> PolicyEvaluationResult:
    # Order matters: check the cheapest rejections first

    if service_requires_manual_gate:
        return PolicyEvaluationResult(
            False, True, "Service is configured for mandatory human sign-off."
        )

    if confidence_score < 0.75:
        return PolicyEvaluationResult(
            False, True,
            f"Model confidence ({confidence_score:.2f}) below 0.75 threshold."
        )

    if proposed_action not in AUTO_EXECUTION_ALLOWLIST:
        return PolicyEvaluationResult(
            False, True,
            f"Action '{proposed_action}' is not on the autonomous allowlist."
        )

    if action_risk == ImpactRisk.HIGH:
        return PolicyEvaluationResult(
            False, True,
            "High blast-radius remediation flagged for SRE review."
        )

    # All four conditions passed — auto-execute
    return PolicyEvaluationResult(True, False, None)

The frozen=True dataclass is intentional. The policy result is immutable — once the gate has decided, nothing downstream can modify the decision. The gate's output is a record, not a mutable state.

Runbooks are retrieved by embedding similarity over a ChromaDB vector store, not by rule matching. This means runbooks can be written as prose — "If the payment service shows a memory leak pattern with rising GC pressure, restart the worker pool and check for connection pool exhaustion" — and the agent finds them by semantic proximity to the alert context. The trade-off: a semantically close but wrong runbook can be retrieved. The policy gate doesn't depend on the runbook being correct — it depends on the action being on the allowlist.

05 What Went Wrong

💥 Things that broke before the system worked
  • Propose-and-execute in one node. The first version had no boundary between diagnosis and execution. Diagnosis: if the model is wrong, the action runs anyway. Fix: split into two nodes — the reasoning agent proposes, the policy gate decides. The agent has no Docker SDK access.
  • Confidence alone is not a safety boundary. 0.88 confidence on a container restart is fine. 0.88 on a database failover is not. Diagnosis: confidence measures the model's certainty about the diagnosis, not the risk of the action. Fix: the four-condition gate — confidence is only one of four conditions. The action's blast radius and allowlist membership are independent checks.
  • The black box problem. After a test incident, I couldn't tell why the agent had chosen to restart a specific container. Diagnosis: no audit trail. Fix: every decision — alert payload, retrieved runbook ID, confidence score, each gate condition's pass/fail, execution result — is written to a PostgreSQL transaction log. The audit trail is not optional; it's the difference between a tool and a rogue agent.
  • Wrong runbook retrieval. ChromaDB returned a semantically close but incorrect runbook for a network error — it suggested a container restart when the real issue was a misconfigured sidecar. Diagnosis: embedding similarity doesn't guarantee correctness. Accepted trade-off: the policy gate doesn't depend on the runbook being correct. If the proposed action isn't on the allowlist, it goes to the human queue regardless of which runbook was retrieved.
💡 The Takeaway

When an AI acts on infrastructure, the proposal and the execution must be separated by a deterministic gate that the AI cannot influence. The gate should be conjunctive (all conditions must pass) and conservative (default to human approval). The audit trail is not optional — it's the difference between a tool and a rogue agent. And confidence measures the model's certainty, not the action's risk. Those are two different axes.

Verified against four simulated fault scenarios: 4/4 action-correctness and 4/4 policy-correctness. The demo services are deliberately faulty — the evidence establishes that the policy gate behaves as specified, not that the agent has run production infrastructure unattended.

A single-process design that works in dev will fail in production when you add workers. Ask: "what breaks when two processes serve the same resource?" The answer is always: anything in process-local memory.

01 The Problem: The Multi-Worker Socket Wall

In development, the chat server was a Python dictionary: active_rooms[room_id] = [ws1, ws2]. One process, one dict, messages fan out to every socket in the room. It worked perfectly.

Then I deployed with 4 Uvicorn worker processes behind Nginx, and it broke immediately:

  • Worker isolation barrier. Client A connected to Worker 1, Client B connected to Worker 2. Both joined Room 101. Client A sent a message. Worker 1's dict had {ws_A} — no reference to Client B. Client B never received the message. The dict only reached sockets on the same process.
  • Subscription explosion. If every worker subscribed to all 5,000 chat rooms in Redis on boot, Redis memory and network I/O were saturated with idle channel overhead — most rooms had zero active users on any given worker.
  • Unauthenticated socket floods. If authentication happened after await websocket.accept(), an attacker could open thousands of idle TCP sockets without sending credentials, exhausting server file descriptors.
✏ Before you read on

Client A connects to Worker 1, Client B connects to Worker 2. Both join Room 101. Client A sends a message. How does Client B receive it? And how do you keep Redis from subscribing to all 5,000 rooms when most are empty on any given worker? Sketch the delivery path and the subscription lifecycle — when does a subscription open, and when does it close?

Use Redis pub/sub as a message broker between workers. Each room gets one Redis channel: room:101. When a message arrives, the worker publishes it to the Redis channel — not to local sockets. Every worker that has a local connection in that room listens on that channel and fans out to its own sockets. The subscription lifecycle is reference-counted: a worker subscribes to room:101 only when its first local client joins that room, and unsubscribes when its last local client leaves. This means Redis only carries channels for rooms that have active participants on each worker — no idle subscriptions, no explosion. Messages always go through Redis even when sender and recipient share a worker, so there's one delivery path to reason about and test.

02 What I Tried First

The in-memory dict worked fine in development and I shipped it to production with 4 workers. The first bug report: "messages don't arrive." I spent an hour thinking the WebSocket connection was broken before realising the dict was per-process. Worker 1's dict had no reference to Worker 2's sockets.

The fix was obvious — add Redis. But the first Redis implementation subscribed every worker to every room on boot. With 5,000 rooms and 4 workers, that was 20,000 subscriptions carrying idle overhead. Redis memory climbed and the pub/sub listener loop spent most of its time ignoring messages for rooms with no local connections.

The third problem I didn't even notice until I read about it: authentication was happening after websocket.accept(). The socket was open before the JWT was checked. An attacker could open thousands of sockets and never send a token.

03 The Decision

In-memory dict per worker
Messages don't cross worker boundaries. The dict only reaches sockets on the same process.
✗
Subscribe to all rooms on boot
Redis memory and I/O saturated with idle channels. Most rooms have zero active users on any given worker.
✗

Attackers open thousands of idle TCP sockets without credentials. File descriptor exhaustion.
✓

The reference-counting pattern is the key insight. A worker subscribes to a room's Redis channel only when it has its first local connection to that room, and unsubscribes when its last local connection leaves. Redis only carries channels for rooms that have active participants on each worker. Messages always go through Redis — even when sender and recipient share a worker — so there's one delivery path to reason about and test.

The connection manager handles authentication, joining, leaving, and the pub/sub listener:

📄 server/manager.py — Reference-Counted Connection Manager 
import asyncio
import json
from typing import Dict, Set, Optional
from fastapi import WebSocket, status
import redis.asyncio as aioredis
import jwt

class DistributedConnectionManager:
    def __init__(self, redis_url: str, jwt_secret: str):
        self.redis = aioredis.from_url(redis_url, decode_responses=True)
        self.pubsub = self.redis.pubsub()
        self.jwt_secret = jwt_secret
        self.local_rooms: Dict[str, Set[WebSocket]] = {}
        self.listener_task: Optional[asyncio.Task] = None

    async def authenticate_and_accept(self, websocket: WebSocket, token: str) -> Optional[str]:
        """Validate JWT BEFORE accepting — invalid tokens never open a socket."""
        try:
            payload = jwt.decode(token, self.jwt_secret, algorithms=["HS256"])
            user_id = payload.get("sub")
            await websocket.accept()
            return user_id
        except jwt.PyJWTError:
            await websocket.close(code=status.WS_1008_POLICY_VIOLATION)
            return None

    async def join_room(self, room_id: str, websocket: WebSocket):
        if room_id not in self.local_rooms:
            self.local_rooms[room_id] = set()
            # First local joiner → subscribe to this room's Redis channel
            await self.pubsub.subscribe(f"room:{room_id}")
            if not self.listener_task or self.listener_task.done():
                self.listener_task = asyncio.create_task(self._pubsub_listener())
        self.local_rooms[room_id].add(websocket)

    async def leave_room(self, room_id: str, websocket: WebSocket):
        if room_id in self.local_rooms:
            self.local_rooms[room_id].discard(websocket)
            if not self.local_rooms[room_id]:
                # Last local client left → release the Redis subscription
                del self.local_rooms[room_id]
                await self.pubsub.unsubscribe(f"room:{room_id}")

    async def broadcast_to_room(self, room_id: str, message: dict):
        """Publish to Redis — never write straight to local sockets."""
        await self.redis.publish(f"room:{room_id}", json.dumps(message))

    async def _pubsub_listener(self):
        """Background loop: receive Redis messages, fan out to local sockets."""
        async for msg in self.pubsub.listen():
            if msg["type"] == "message":
                room_id = msg["channel"].removeprefix("room:")
                data = json.loads(msg["data"])
                if room_id in self.local_rooms:
                    sockets = list(self.local_rooms[room_id])
                    await asyncio.gather(
                        *[s.send_json(data) for s in sockets],
                        return_exceptions=True
                    )

Messages go through Redis even when sender and recipient are on the same worker. The trade-off: a round trip on every message. The payoff: one delivery path to reason about and test. There's no "same-worker shortcut" branch in the code.

History uses cursor-based pagination. The traditional LIMIT 15 OFFSET 30 introduces drift: as new messages arrive, the offset shifts and users see duplicates or gaps. The cursor is a composite tuple (created_at, id) — stable under insertion:

📄 server/queries.sql — Stable Cursor Pagination 
-- Immune to active message insertion: the cursor is a fixed point,
-- not a count from the top of a changing table.
SELECT id, room_id, user_id, message_text, created_at
FROM messages
WHERE room_id = :room_id
  AND (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 15;

Presence is a Redis hash counter per user, not a boolean. If the same person opens two tabs, they're counted once — the counter increments on join and decrements on leave. The trade-off: if a worker dies without cleaning up, the counter never decrements and the user shows as online indefinitely. A TTL on the presence key would fix this, but it's a known limitation in the current build.

05 What Went Wrong

💥 Things that broke before the system worked
  • Messages not arriving across workers. The in-memory dict only reached sockets on the same process. Diagnosis: I thought the WebSocket was broken and spent an hour debugging the connection before realising the dict was per-process. Fix: Redis pub/sub. Messages publish to a room channel; every worker with a local connection in that room fans out to its own sockets.
  • Subscription explosion. First Redis implementation subscribed every worker to every room on boot — 20,000 subscriptions for 5,000 rooms. Diagnosis: Redis memory climbed steadily. Fix: reference counting. Subscribe on first local joiner, unsubscribe on last local leaver. Redis only carries channels for rooms with active participants on each worker.
  • Unauthenticated socket floods. Authentication was after websocket.accept(). Diagnosis: I hadn't thought about it — I was focused on message delivery. Fix: move JWT verification before accept(). Invalid tokens get WS_1008_POLICY_VIOLATION and never open a socket.
  • Offset pagination drift. LIMIT 15 OFFSET 30 shifted as new messages arrived — users saw duplicates or gaps. Diagnosis: the offset is a count from the top of a changing table. Fix: cursor-based pagination on (created_at, id). The cursor is a fixed point, not a count. Pages stay stable under insertion.
  • Presence as boolean. Same person on two tabs was counted as two people. Diagnosis: a boolean can't distinguish "one person with two tabs" from "two people." Fix: a Redis hash counter per user. Join increments, leave decrements. The person is present while the counter is above zero.
  • Redis subscriber connection drops silently. If a worker's Redis subscriber connection drops, that process stops receiving room messages — with no error raised. This is a known limitation: there's no health check on the pub/sub connection in the current build.
💡 The Takeaway

A single-process design that works in dev will almost always fail in production when you add workers. Ask: "what breaks when two processes serve the same resource?" The answer is always: anything held in process-local memory. Redis pub/sub solves delivery. Reference counting solves resource pressure. Authentication before accept solves the security boundary. Cursor pagination solves history stability. Each fix came from a specific failure — not from foresight.
