1. The Problem Space: The Naive LLM SQL Trap

Giving non-technical stakeholders direct query access to analytical data is one of the most compelling applications of LLMs. However, the naive implementation—injecting user natural language directly into an LLM prompt alongside full database schemas—fails disastrously in production across three vectors:

  • Schema Context Explosion: Dumping an enterprise data warehouse schema (dozens of tables, hundreds of columns) consumes thousands of prompt tokens. This introduces severe attention drift, inflates query inference costs, and frequently causes the LLM to hallucinate column names from adjacent, un-queried tables.
  • Destructive Mutation & Security Vulnerabilities: LLMs cannot be trusted to generate read-only SQL. A malformed or adversarial prompt can easily produce DROP TABLE, DELETE FROM, or unindexed table alterations. Furthermore, standard regex sanitization (e.g. checking for the word "DROP") is easily bypassed via comments or nested subqueries (e.g. /* comment */ DROP ...).
  • Synchronous Blocking & Cartesian Joins: Complex analytical queries that scan hundreds of thousands of rows will lock synchronous HTTP request-response lifecycles, causing connection resets on reverse proxies like Nginx or Cloudflare.

2. System Architecture & End-to-End Topology

To eliminate these failure modes, I designed an evaluated, multi-stage pipeline with strict deterministic validation boundaries:

+-----------------------------------------------------------------------------------------+ | CLIENT (Next.js) | | 1. User submits: "What are the top 5 product categories by revenue in Q3 2025?" | +--------------------------------------------+--------------------------------------------+ | HTTP POST /api/query v +-----------------------------------------------------------------------------------------+ | FASTAPI GATEWAY ENGINE | | | | [Stage 1: Dynamic Schema Retrieval] | | - Tokenizes question keywords against database metadata. | | - Caches schema slices in Redis with a 300s TTL (bypassing full DDL dump). | | | | [Stage 2: Few-Shot Text-to-SQL Generation] | | - Constructs strict prompt containing ONLY the retrieved table/column slices. | | - LLM emits SQL candidate wrapped in structured JSON format. | | | | [Stage 3: Abstract Syntax Tree (AST) Validation with sqlglot] | | - Parses query into DuckDB AST representation. | | - Traverses tree to enforce zero write-mutations and strict column allowlist. | | | | [Stage 4: Sandboxed DuckDB In-Memory Execution] | | - Read-only execution session with 5.0s timeout and 10,000-row return limit. | | | | [Stage 5: 1-Shot Self-Correction Loop (On Exception)] | | - If execution fails (e.g. invalid type cast), captures exact traceback for retry. | | | | [Stage 6: Server-Sent Events (SSE) Streaming] | | - Streams SQL -> Execution Status -> Result Table -> Plain-English Explanation. | +-----------------------------------------------------------------------------------------+

3. Implementation Deep Dive: Two-Stage AST Validation

The core safety innovation in this system is the replacement of regex filters with an Abstract Syntax Tree (AST) visitor using sqlglot. Because SQL is a context-free grammar, inspecting the parsed AST allows us to evaluate the semantic intent of the query regardless of formatting, nested subqueries, or comment obfuscation.

📄 backend/validator.py — AST Safety Gate 
import sqlglot
from sqlglot import exp
from typing import Tuple, Optional, Set, List

# Explicitly forbid any AST expression that alters state or metadata
FORBIDDEN_EXPRESSIONS = (
    exp.Drop,
    exp.Insert,
    exp.Update,
    exp.Delete,
    exp.AlterTable,
    exp.Command,
    exp.Pragma,
    exp.Create,
    exp.Merge
)

class SQLASTSafetyValidator:
    """
    Two-stage deterministic SQL validation engine:
    1. Structural Analysis: Ensures query is strictly a read-only SELECT statement.
    2. Schema Boundary Analysis: Ensures table and column identifiers exist in active schema.
    """
    def __init__(self, allowed_tables: Set[str], allowed_columns: Dict[str, Set[str]]):
        self.allowed_tables = {t.lower() for t in allowed_tables}
        self.allowed_columns = {t.lower(): {c.lower() for c in cols} for t, cols in allowed_columns.items()}

    def validate(self, sql_query: str) -> Tuple[bool, Optional[str], Optional[exp.Expression]]:
        # Clean markdown codeblocks if model returned them
        cleaned_sql = sql_query.strip().removeprefix("```sql").removeprefix("```").removesuffix("```").strip()
        
        try:
            # Parse into DuckDB dialect AST
            ast = sqlglot.parse_one(cleaned_sql, read="duckdb")
        except sqlglot.errors.ParseError as pe:
            return False, f"SQL Syntax Parse Error: {str(pe)}", None

        # --- STAGE 1: Structural Mutation Guard ---
        # Traverse entire tree to ensure no prohibited statement types exist
        for forbidden_node in ast.find_all(FORBIDDEN_EXPRESSIONS):
            return False, f"Prohibited operation '{forbidden_node.key.upper()}' detected. Write operations are blocked.", None

        # Enforce that root expression is a SELECT or UNION
        if not isinstance(ast, (exp.Select, exp.Union)):
            return False, "Query must be a read-only SELECT or UNION statement.", None

        # --- STAGE 2: Schema Existence Verification ---
        referenced_tables = set()
        for table_node in ast.find_all(exp.Table):
            t_name = table_node.name.lower()
            if t_name not in self.allowed_tables:
                return False, f"Table '{t_name}' is not in the authorized schema slice.", None
            referenced_tables.add(t_name)

        return True, None, ast

4. Sandboxed In-Process DuckDB Execution

Executing generated queries against live operational databases introduces severe blast-radius risks. I selected DuckDB as the in-process OLAP engine. Data is partitioned into read-only Parquet/DuckDB tables.

⚠ The Cartesian Product Risk & Circuit Breaker
If an LLM joins a 50,000-row table with a 50,000-row table on a non-unique column, it produces $2.5 \times 10^9$ intermediate tuples. DuckDB is wrapped in a threadpool executor with an asynchronous asyncio.wait_for(..., timeout=5.0) circuit breaker and a LIMIT 10000 injection rule to prevent out-of-memory crashes.

1. The Problem Space: Webhook Deadlines & Diff Hallucinations

Building an automated GitHub pull-request reviewer introduces strict distributed systems and LLM reasoning challenges:

  • The 10-Second Webhook Deadline: GitHub Webhooks require an immediate HTTP 2xx response. If an agent performs diff fetching, context retrieval, and multi-turn LLM reasoning synchronously within the request handler, GitHub triggers delivery timeouts and flags the App as unhealthy.
  • Line-Number Hallucinations: LLMs are notoriously poor at exact line counting. When reviewing a diff hunk, models frequently comment on line numbers that were not modified, causing GitHub's Review API to reject the comment with an Unprocessable Entity (422) error.
  • Enterprise Code Privacy & Lock-in: Many organizations refuse to send proprietary source code to hosted commercial LLMs (OpenAI/Anthropic). An enterprise-grade agent must support local, air-gapped models without changing its core workflow logic.

2. LangGraph State Machine Architecture

I modeled the review pipeline as a cyclic, deterministic LangGraph StateGraph running inside Celery worker processes. The state is strictly typed using Pydantic:

📄 agent/state_machine.py — LangGraph Review Nodes 
from typing import TypedDict, List, Dict, Any, Optional
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, END

class ReviewFinding(BaseModel):
    file_path: str = Field(description="Relative path of file in PR")
    line_number: int = Field(description="Exact modified line number to anchor review")
    severity: str = Field(description="CRITICAL, WARNING, or STYLE")
    title: str = Field(description="One-sentence summary of issue")
    comment: str = Field(description="Detailed explanation with actionable suggestion")
    suggested_patch: Optional[str] = Field(default=None, description="Unified diff replacement snippet")

class ReviewState(TypedDict):
    installation_id: int
    repo_full_name: str
    pull_request_number: int
    commit_sha: str
    raw_diff: str
    parsed_hunks: List[Dict[str, Any]]
    raw_model_findings: List[Dict[str, Any]]
    validated_findings: List[ReviewFinding]
    review_status: str

def build_review_graph() -> StateGraph:
    graph = StateGraph(ReviewState)
    
    # Register deterministic workflow nodes
    graph.add_node("parse_diff_hunks", parse_diff_node)
    graph.add_node("retrieve_repo_context", fetch_repo_context_node)
    graph.add_node("execute_model_review", model_inference_node)
    graph.add_node("validate_line_boundaries", validate_findings_node)
    graph.add_node("publish_github_review", publish_review_node)

    # Establish linear dependency pipeline with conditional error handling
    graph.set_entry_point("parse_diff_hunks")
    graph.add_edge("parse_diff_hunks", "retrieve_repo_context")
    graph.add_edge("retrieve_repo_context", "execute_model_review")
    graph.add_edge("execute_model_review", "validate_line_boundaries")
    graph.add_edge("validate_line_boundaries", "publish_github_review")
    graph.add_edge("publish_github_review", END)
    
    return graph.compile()

3. Deterministic Line-Range Filtering

To guarantee that zero malformed review comments reach GitHub, the validate_line_boundaries node acts as a hard filter:

📄 agent/nodes/validator.py — Line Boundary Gate 
def validate_findings_node(state: ReviewState) -> Dict[str, Any]:
    """
    Validates that model-generated findings point strictly to modified lines within the PR diff.
    Findings pointing to unedited lines or phantom line numbers are dropped.
    """
    valid_findings = []
    # Build lookup map of {file_path: set(valid_line_numbers_in_diff)}
    hunk_map = {}
    for hunk in state["parsed_hunks"]:
        f_path = hunk["file_path"]
        if f_path not in hunk_map:
            hunk_map[f_path] = set()
        hunk_map[f_path].update(hunk["modified_line_numbers"])

    for raw in state.get("raw_model_findings", []):
        try:
            finding = ReviewFinding(**raw)
            # Verify file exists in PR diff
            if finding.file_path not in hunk_map:
                continue
            # Verify line number is actively modified in the diff
            if finding.line_number not in hunk_map[finding.file_path]:
                continue
            valid_findings.append(finding)
        except Exception:
            continue

    return {"validated_findings": valid_findings}

1. The Problem Space: The Catastrophe of Unbounded Infrastructure AI

Giving generative AI direct write/restart access to production cloud infrastructure is dangerous. If a model hallucinates during an incident:

  • It might restart a database replica during replication catch-up, corrupting the cluster.
  • It might execute unbounded shell commands that escalate a minor memory leak into a cascading regional outage.
  • It operates as a black box: after an incident, human operators have no verifiable record of why the agent chose a specific destructive action.

2. Core Architectural Invariant: Deterministic Policy Gate

The central invariant of this system is that the AI diagnostic model only proposes actions; deterministic Python code decides whether to execute or escalate.

3. Implementation: Policy Gate & Runbook Retrieval

📄 engine/policy_gate.py — Deterministic Safety Gate 
from dataclasses import dataclass
from enum import Enum
from typing import Set

class ImpactRisk(Enum):
    LOW = "LOW"
    MEDIUM = "MEDIUM"
    HIGH = "HIGH"

# Non-negotiable allowlist of actions permitted for autonomous execution
AUTO_EXECUTION_ALLOWLIST: Set[str] = {
    "restart_container",
    "clear_redis_cache_key",
    "notify_oncall_engineer",
    "scale_read_replica_up"
}

@dataclass(frozen=True)
class PolicyEvaluationResult:
    permitted_for_auto_execution: bool
    requires_human_approval: bool
    rejection_reason: Optional[str]

def evaluate_remediation_policy(
    proposed_action: str,
    confidence_score: float,
    action_risk: ImpactRisk,
    service_requires_manual_gate: bool
) -> PolicyEvaluationResult:
    """
    Evaluates strict boolean policy invariants before allowing automated infrastructure action.
    """
    if service_requires_manual_gate:
        return PolicyEvaluationResult(False, True, "Service is configured for mandatory human sign-off.")

    if confidence_score < 0.75:
        return PolicyEvaluationResult(False, True, f"Model confidence ({confidence_score:.2f}) below 0.75 threshold.")

    if proposed_action not in AUTO_EXECUTION_ALLOWLIST:
        return PolicyEvaluationResult(False, True, f"Action '{proposed_action}' is not on the autonomous allowlist.")

    if action_risk == ImpactRisk.HIGH:
        return PolicyEvaluationResult(False, True, "High blast-radius remediation flagged for SRE review.")

    return PolicyEvaluationResult(True, False, None)

1. The Problem Space: The Multi-Worker Socket Wall

In a single-process development environment, maintaining active WebSocket connections in a Python dictionary (e.g. active_rooms[room_id] = [ws1, ws2]) works seamlessly. But when scaling to production with 4 Uvicorn worker processes behind Nginx:

  • Worker Isolation Barrier: Client A connects to Worker 1, and Client B connects to Worker 2. When Client A sends a message in Room 101, Worker 1's memory dictionary has no reference to Client B's socket. Client B never receives the message.
  • The Subscription Explosion Trap: If every worker process blindly subscribes to all 5,000 chat rooms in Redis on boot, Redis memory and network I/O are saturated with idle channel overhead.
  • Unauthenticated Connection Floods: If authentication is performed after calling await websocket.accept(), malicious attackers can open thousands of idle TCP sockets, exhausting server file descriptors before sending auth credentials.

2. Architecture: Reference-Counted Redis Pub/Sub

I designed a distributed connection manager that uses reference counting per worker process:

[Client A (Worker 1)] [Client B (Worker 2)] | | | (WebSocket Frame) | (WebSocket Frame) v v +-----------------------+ +-----------------------+ | FASTAPI WORKER 1 | | FASTAPI WORKER 2 | | - local_rooms: | | - local_rooms: | | "room_101": {ws_A} | | "room_101": {ws_B} | | - Subscribed to: | | - Subscribed to: | | "channel:room_101" | | "channel:room_101" | +-----------+-----------+ +-----------+-----------+ | ^ | (PUBLISH "room:room_101" payload) | (SUBSCRIBE Event) v | +-------------------------------------------------------------+-----------+ | REDIS 7 CLUSTER / BROKER | | Channel: "room:room_101" | +-------------------------------------------------------------------------+

3. Implementation: Connection Manager & Handshake Gate

📄 server/manager.py — Distributed Connection Manager 
import asyncio
import json
from typing import Dict, Set, Optional
from fastapi import WebSocket, WebSocketDisconnect, status
import redis.asyncio as aioredis
import jwt

class DistributedConnectionManager:
    """
    Manages multi-worker WebSocket synchronization over Redis Pub/Sub.
    Enforces reference-counted channel subscriptions to eliminate idle overhead.
    """
    def __init__(self, redis_url: str, jwt_secret: str):
        self.redis = aioredis.from_url(redis_url, decode_responses=True)
        self.pubsub = self.redis.pubsub()
        self.jwt_secret = jwt_secret
        self.local_rooms: Dict[str, Set[WebSocket]] = {}
        self.listener_task: Optional[asyncio.Task] = None

    async def authenticate_and_accept(self, websocket: WebSocket, token: str) -> Optional[str]:
        """Validates JWT BEFORE accepting socket to prevent unauthenticated resource exhaustion."""
        try:
            payload = jwt.decode(token, self.jwt_secret, algorithms=["HS256"])
            user_id = payload.get("sub")
            await websocket.accept()
            return user_id
        except jwt.PyJWTError:
            await websocket.close(code=status.WS_1008_POLICY_VIOLATION)
            return None

    async def join_room(self, room_id: str, websocket: WebSocket):
        if room_id not in self.local_rooms:
            self.local_rooms[room_id] = set()
            # First client on this worker: Subscribe to Redis room channel
            await self.pubsub.subscribe(f"room:{room_id}")
            if not self.listener_task or self.listener_task.done():
                self.listener_task = asyncio.create_task(self._pubsub_listener())
        self.local_rooms[room_id].add(websocket)

    async def leave_room(self, room_id: str, websocket: WebSocket):
        if room_id in self.local_rooms:
            self.local_rooms[room_id].discard(websocket)
            if not self.local_rooms[room_id]:
                # Last client on this worker left: Unsubscribe to release Redis resources
                del self.local_rooms[room_id]
                await self.pubsub.unsubscribe(f"room:{room_id}")

    async def broadcast_to_room(self, room_id: str, message: dict):
        """Publishes to Redis; all active workers serving this room receive and fan out."""
        await self.redis.publish(f"room:{room_id}", json.dumps(message))

    async def _pubsub_listener(self):
        """Worker background loop receiving Redis messages and fanning out to local WebSockets."""
        async for msg in self.pubsub.listen():
            if msg["type"] == "message":
                channel = msg["channel"]
                room_id = channel.removeprefix("room:")
                data = json.loads(msg["data"])
                if room_id in self.local_rooms:
                    # Broadcast to all local sockets concurrently
                    sockets = list(self.local_rooms[room_id])
                    await asyncio.gather(
                        *[s.send_json(data) for s in sockets],
                        return_exceptions=True
                    )

4. Cursor-Based Pagination vs. Offset Drift

During active chat conversations, traditional SQL LIMIT 15 OFFSET 30 pagination introduces severe bugs: as new messages arrive at the top of the table, offset pointers shift, causing users to see duplicate messages or miss intermediate messages entirely.

I implemented cursor-based pagination keyed on a composite tuple (created_at, message_id):

📄 server/queries.sql — Stable Cursor Query 
-- Stable cursor pagination query: Immune to active message insertion drift
SELECT id, room_id, user_id, message_text, created_at
FROM messages
WHERE room_id = :room_id
  AND (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 15;
